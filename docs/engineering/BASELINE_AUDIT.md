**سلسلة التنبيه الحرج (`shell-quote`):**
```
smartschool@1.0.0 → react-native@0.81.5 → react-devtools-core@6.1.5 → shell-quote@1.10.0
```
- **الوصولية:** كود التطبيق في `app/` لا يستدعي `react-devtools-core` ولا `shell-quote`؛ المسار يخدم أدوات تطوير React Native. الثغرة **ليست قابلة للاستغلال في حزمة التطبيق المُصدَّرة**، لكنها تظل في شجرة الاعتماديات المعلنة كإنتاج.

- **الخلاصة:** إجراء سليم واحد متاح الآن: توثيق التنبيهات، ومتابعة تحديث `expo`/`react-native` ضمن دورتها الطبيعية، وإضافة Dependabot (لاحقاً، بموافقة). **عدد التنبيهات ليس مقياس خطر بحد ذاته**، ومسارات الأدوات لا تُضاعف خطر الحزمة النهائية.

## 10. خطة P0 المقترحة (تُعرض قبل أي تنفيذ، مع ما هو قابل للتنفيذ في هذه البيئة)

> القاعدة: كل بند له اختبار قبول مكتوب. البنود التي تحتاج .NET SDK **لن يُدّعى نجاحها**.

### P0-A — حماية تسجيل الدخول (تقسيم الحصص + حماية تدريجية)
1. استبدال `AddFixedWindowLimiter("login")` بسياسة **مقسّمة**: قسم لكل هوية مستخدم (اسم المستخدم) + قسم لكل IP، مع حدّين منفصلين.
2. استخراج IP من `HttpContext.Connection.RemoteIpAddress` فقط، وتفعيل `UseForwardedHeaders` **مقيّداً بوسطاء مُعلَّقين** (لا ثقة عمياء بـ `X-Forwarded-For`).
3. حماية تدريجية للمحاولات الفاشلة: تأخير متزايد + قفل **مؤقت** (مثل 15 دقيقة) مربوط بالمستخدم، مع عدّاد دقيق في `AuditLogs`، ومنع إساءة استخدام القفل كسلاح (القفل لا يُمدَّد بطلبات الفشل من مصدر مختلف).
4. اختبارات جديدة: 429 بعد تجاوز الحد، استقلال حصّتين لعميلين مختلفين، عدم تأثر عميل بعميل آخر، عدم تسرب التفاصيل في الردود، واستمرار نجاح اختبارات الدخول الحالية.
- **قابل للتنفيذ هنا:** كتابة الكود + الاختبارات. **غير قابل:** تشغيلها (لا SDK) → ستُشغَّل في CI.

### P0-B — فرادة أسماء المستخدمين
1. تحديد قاعدة التطبيع (Trim + مقارنة بلا حساسية لحالة الأحرف) وتوثيقها.
2. **التحقق من وجود تكرارات في قاعدة فعلية لا يمكن محلياً** (لا ملف قاعدة) ⇒ مطلوب تصدير/استعلام قراءة فقط من المالك. **هذا مانع لقرار الترحيل.**
3. إنشاء ترحيل يضيف فهرساً فريداً (`Username` مطبَّع) — **مع مسار آمن للبيانات المتعارضة**: لا إعادة تسمية ولا حذف تلقائي؛ الترحيل يفشل بوضوح ويُخرج تقرير تعارضات بلا بيانات حسّاسة.
4. منع 500 عند التكرار: `SingleOrDefaultAsync` → `FirstOrDefaultAsync` + فحص تكرار في كل مسارات الإنشاء + معالجة استثناء الفهرس الفريد كـ 409.
5. اختبارات: إنشاء مكرّر عبر كل مسار (طالب/معلم/وصي) ⇒ 409، سباق إنشاء متزامن ⇒ لا تكرار، ودخول سليم بعد التغيير.

### P0-C — توحيد إعداد قاعدة البيانات
1. مصدر واحد: `ConnectionStrings:Default` في `appsettings.json` + تجاوز عبر متغيّر بيئة (`SMARTSCHOOL_DB_CONNECTION`)، مع قيمة افتراضية للتطوير.
2. توحيد مصنع وقت التصميم ليقرأ نفس المفتاح ⇒ **CI يتحقق من قاعدة التطبيق نفسها**.
3. منع تسريب أي إعداد اتصال في Git (لا أسرار في `appsettings`).
4. اختبار يثبت أن مسار التطبيق ومسار الترحيلات متطابقان.
5. **لا تحويل إلى PostgreSQL ولا نقل بيانات في هذه المرحلة** (يحتاج موافقة المالك وقراراً مستقلاً).

### P0-D — التحقق من الهوية بين الخدمتين (إصلاحات غير معمارية)
1. اختبارات تُثبّت السلوك الحالي: رمز الـ API الرئيسي **مرفوض** في خدمة AI، ورمز منتهٍ/مزوّر مرفوض.
2. تشديد التحقق في FastAPI: قراءة الإعداد من البيئة فقط، رفض المفاتيح القصيرة (موجود)، وإضافة تتبّع للمستخدم في السجل.
3. **توثيق الخيارين** (وسيط موثوق عبر ASP.NET Core مقابل خدمة مستقلة بعقد ثقة موحّد) بمقارنة أمان/صيانة/نشر/عزل مدارس/تسجيل/اختبارات — **والقرار للمالك قبل أي دمج للهويتين**.
