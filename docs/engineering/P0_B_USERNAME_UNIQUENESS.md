## 2. سياسة التطبيع **الحالية** (ثلاث دلالات مختلفة لنفس السؤال!)

| الموضع | المقارنة المستخدمة | السلوك الفعلي |
|---|---|---|
تسجيل الدخول (`AuthController.cs:25`) | `u.Username == request.Username` | EF Core ⇒ SQL `=`. **حساس لحالة الأحرف ولا يقلّم** |
مسار الأوصياء (الإنشاء) | `AnyAsync(x => x.Username == command.Username)` + `Trim()` | حساس للحالة، **مقلَّم** عند التخزين |
كتم المحاولات (`LoginAttemptThrottle.Normalize`) | `Trim().ToLowerInvariant()` | **غير حساس للحالة، مقلَّم** |

**إثبات تنفيذي لسلوك التخزين (SQLite، محلياً):**
```
SELECT COUNT(*) FROM Users WHERE Username='admin'   -> 1
SELECT COUNT(*) FROM Users WHERE Username='ADMIN'   -> 0     # مقارنة ثنائية BINARY
CREATE UNIQUE INDEX ux ON Users(Username)           -> UNIQUE constraint failed: Users.Username
```
**النتائج العملية:**
1. مستخدم أُنشئ باسم `Ahmed` **لا يستطيع** الدخول بـ`ahmed` (401) — بينما الكتم يعامل الاسمين كحساب واحد.
2. مساحة بيضاء في نهاية الاسم عند الدخول ⇒ 401 (لأن الدخول لا يقلّم)، بينما المسافات تُخزَّن فعلاً في مسارَي الطالب/المعلم.
3. تكرار **مطابق** واحد يكفي لتعطيل الدخول للحساب: `SingleOrDefaultAsync` يرمي استثناءً ⇒ **500** (وليس 401).

## 4. أداة فحص التكرارات للبيانات الفعلية (قراءة فقط)

`SmartSchoolAPI/Tools/find_duplicate_usernames.py` — تُشغَّل على **نسخة** من قاعدة الإنتاج:

```bash
python SmartSchoolAPI/Tools/find_duplicate_usernames.py "/path/to/copy of school_system.db"
python SmartSchoolAPI/Tools/find_duplicate_usernames.py DB --json --mask
```

- تفتح القاعدة بـ`mode=ro` (قراءة فقط)، ولا تُنشئ معاملة كتابة، ولا تطبع أي تجزئة كلمة مرور.
- تُصنّف التعارضات: **مطابق** (يعطّل الدخول بـ500) · **يختلف بحالة الأحرف** · **يختلف بالمسافات** · **أسماء مبطّنة بمسافات**.
- تُجيب سؤالين حاسمين: `safe to add UNIQUE(Username)` و`safe to add normalized unique index`.
- رموز الخروج: `0` نظيفة · `2` يوجد تعارض · `1` خطأ/جدول مفقود.
- **مُختبرة فعلياً** على قواعد اصطناعية: نظيفة ⇒ 0، متعارضة ⇒ 2 (كشفت 1 مطابق + 2 حالة أحرف + 1 مسافات + 1 مبطّن)، وبصمة الملف (`md5`) لم تتغيّر بعد التشغيل.

## 5. التصميم المقترح للآلية الموحّدة

### 5.1 سياسة التطبيع (مقترحة): `Normalize(u) = u.Trim().ToLowerInvariant()`
- سبب اختيارها: تطابق سلوك الكتم الحالي (P0-A)، وتتوافق مع توقّع المستخدم (لا فرق بين `Ahmed` و`ahmed`)، وتمنع المسافات المخفية.
- ملاحظة: `ToLowerInvariant` بلا ثقافة محلية (تفادي مشكلة الحرف I التركي).
- **تغيير سلوكي يجب إقراره:** يصبح الدخول **غير حساس لحالة الأحرف**. هذا تحسين متوقّع، لكنه تغيير يجب توثيقه للعملاء.

### 5.2 الخطة التقنية (ثلاث طبقات — الدفاع في العمق)
1. **طبقة التطبيق:** دالة تطبيع واحدة مشتركة + فحص فرادة في **كل** مسارات الإنشاء (`/api/students`, `/api/teachers`, `/api/students/{id}/guardians`) ⇒ `409 Conflict` برسالة واضحة.
2. **طبقة قاعدة البيانات:** عمود محسوب/مخزَّن `NormalizedUsername` + **فهرس فريد** عليه. (بديل: فهرس فريد على تعبير `lower(trim(Username))` — مدعوم في SQLite، لكن عموداً صريحاً أوضح للقراءة والتشغيل.)
3. **طبقة معالجة السباق:** ترجمة استثناء الفهرس الفريد (`DbUpdateException`) إلى `409` بدل `500`؛ هذا هو الحارس الوحيد الذي يعمل تحت التزامن الحقيقي.
4. **تعديل مطلوب في الدخول:** البحث بالصيغة المطبَّعة بدل المقارنة الخام، و`SingleOrDefaultAsync` ⇒ `FirstOrDefaultAsync` (مع ضمان الفهرس أنه لن يوجد أكثر من صف).

### 5.3 خطة الترحيل (تُعتمد فقط بعد الموافقة)
```
① فحص مسبق: find_duplicate_usernames.py على نسخة من قاعدة الإنتاج  ← شرط إلزامي
② إن وُجدت تعارضات: يوقف العمل، ويُقدَّم تقرير للمالك (لا إعادة تسمية ولا حذف تلقائي)
③ Migration: إضافة العمود + تعبئته (NormalizedUsername = lower(trim(Username))) + الفهرس الفريد
   - إن فشل الفهرس ⇒ الترحيل يفشل بوضوح ولا يُطبَّق جزئياً على بيانات متعارضة
④ نشر الكود (فحوص التطبيق + 409 + البحث المطبَّع)
⑤ اختبارات ما بعد الترحيل: دخول كل الأدوار، إنشاء مكرّر ⇒ 409، سباق ⇒ 409
```
**العودة (Rollback):** حذف الفهرس والعمود في Migration معاكسة؛ الكود القديم يواصل العمل (المقارنة الخام) بعد إرجاع البحث.

### 5.4 مصفوفة الاختبارات المطلوبة مع التنفيذ (تُضاف لحظة التطبيق)
| الحالة | المتوقع بعد الإصلاح |
|---|---|
إنشاء مطابق ثانٍ (كل مسار) | `409` بدل `200` |
اختلاف حالة الأحرف / مسافات | `409` |
إنشاءان متزامنان لنفس الاسم | واحد `200` والآخر `409` (لا 500) |
دخول بحالة مختلفة عن المخزَّنة | `200` (بعد تغيير السلوك) |
دخول بحساب مكرّر قديم (بيانات لم تُنظَّف) | لا 500 — 401/200 فقط |
اختبارات P0-A كلها | تبقى خضراء |

## 6. التوصية النهائية

1. **نفّذ التطبيع الموحّد + الفهرس الفريد على الاسم المطبَّع** (لا فهرس على الاسم الخام وحده، لأنه لا يمنع اختلاف الحالة/المسافات). القرار الآن **معلّق على موافقتك** وعلى نتيجة الفحص المسبق لقاعدة الإنتاج.
2. **لا تُنفَّذ أي إعادة تسمية أو دمج تلقائي.** التعارضات تُعرض عليك لتقرر سياستها (مثال: تثبيت الحساب الأقدم وتعديل الأحدث يدوياً).
3. **رتبة التنفيذ:** التطبيع + الفحوص في التطبيق أولاً (لا تلمس البيانات)، ثم العمود + الفهرس في Migration منفصلة.
4. **قبل أي ترحيل حقيقي:** شغّل الأداة على نسخة من قاعدة الإنتاج وشاركني الناتج.
