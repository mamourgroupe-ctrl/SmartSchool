# قرارات المرحلة 1: عزل المدارس

آخر تحديث: 27 أكتوبر 2026. هذه القرارات تخص API ‏ASP.NET Core فقط؛ لا تفترض أن خدمة Python المنفصلة تشارك هوية المدارس أو صلاحياتها. لا تُدمج هذه المرحلة قبل مراجعة بشرية أمنية ومراجعة خطة التعامل مع البيانات القديمة.

## مصدر النطاق

- `ISchoolScope` يقرأ هوية وroles الطلب الموثّق من `HttpContext.User`، ثم يتحقق من العضويات الفعالة والعلاقات المخزنة. لا يأخذ معرّف المدرسة أو الدور من رأس أو جسم أو معامل مرسَل من العميل لمنح صلاحية. المعرّفات في المسار تحدد المورد المطلوب فقط وتُفحَص ملكيته بعد ذلك.
- للمشرف العام وصول شامل للقراءة، بما في ذلك السجلات المحجوبة، للمراجعة. مدير المدرسة يرى مدرسته ذات العضوية الفعالة؛ المعلم يرى طلاب شعبه النشطة ذات المدرسة المطابقة؛ ولي الأمر يحتاج عضوية فعالة في مدرسة الطالب ورابطًا مصرحًا؛ الطالب يرى سجله الشخصي المرتبط به. الدور `SUPERVISOR` بلا صلاحيات مدرسية في التطبيق الحالي.
- إنشاء طالب أو معلم من المسارات العامة لا يتضمن مورد مدرسة موثوقًا في المسار، لذا يُسمح به فقط عندما يملك المنفّذ عضوية فعالة في مدرسة واحدة بالضبط؛ وإلا تكون الاستجابة 403. يُنشأ الحساب والملكية والعضوية ضمن معاملة واحدة. إضافة حساب موجود إلى مدرسة مقصورة على المشرف العام، وليست متاحة للمدير بمجرد معرفة معرّف الحساب.

## ملكية صريحة وحجر البيانات السابقة

- يضيف الترحيل `OrganizationId` قابلًا للقيمة الفارغة للطالب والمعلم ولسجلات الحضور والسلوك والقرآن، مع مفاتيح أجنبية. السجل الجديد يأخذ المدرسة من نطاق الطالب المصرَّح به على الخادم. لا يرى غير المشرف العام سجلًا إلا عندما تتطابق مدرسة السجل مع مدرسة الطالب، إضافة إلى صلاحية الدور والعلاقة.
- **تأثير تشغيلي مهم:** الترحيل لا يخمّن ملكية أي صف موجود سابقًا؛ تبقى قيم الملكية الجديدة `NULL`. تُحفظ الصفوف لكنها تُحجب عن وصول المدرسة إلى أن تحدد ملكيتها بعد مراجعة بشرية موثقة. لذلك لن تكون بيانات الطلاب والمعلمين وسجلاتهم القديمة متاحة طبيعيًا للمدارس فور الترقية، وقد تتطلب عملية تسوية كبيرة قبل الإطلاق. ملف الطالب الأساسي غير المرتبط بمدرسة يظل ظاهرًا لصاحبه فقط، دون إتاحة Student 360 أو سجلات المدرسة له.
- لا تعددٌ للعضويات أو وجود تسجيل واحد دليلًا كافيًا بحد ذاته لإسناد كل تاريخ الطالب تلقائيًا: كان النظام السابق يسمح بإضافة عضوية وتسجيل عابرين. ينبغي مراجعة الطالب، المعلم، دوراته وشُعبه، التسجيلات، روابط أولياء الأمور، وكل سجل مستقلًا؛ فالروابط القديمة قد تكون متضاربة أيضًا. تتبع الدورات مدرسة المعلم، لذا لا يُسنَد معلم ذو دورات قديمة حتى يُراجع تاريخها كله؛ لا توجد ملكية منفصلة تسمح بإظهار بعضها وحجر بعضها عبر API الحالية. المشرف العام يستطيع فحص البيانات المحجوبة، لكن لا يوجد endpoint لإسناد تاريخ مجهول جماعيًا.
- تسمح API للمشرف العام بإسناد طالب أو معلم غير مملوك في الإنشاء الأول **فقط** إذا لم توجد له عضوية أو تاريخ ذي صلة؛ لا يجوز استخدامها لاستيلاء مدرسة على تاريخ مجهول. تتطلب تسوية السجلات القديمة إجراءً تشغيليًا منفصلًا، وموافقة بشرية على كل ربط ونسخة احتياطية قابلة للاستعادة. لا تُنفَّذ تحديثات جماعية بالاعتماد على أحدث تسجيل أو معرّف مُرسل من عميل.
- قبل أي ترقية إنتاجية: أوقف الكتابات، خذ نسخة واختبر استعادتها، احصر الصفوف ذات `OrganizationId IS NULL` في الجداول الخمسة، ثم اعتمد خطة تسوية ومراجعة الروابط قبل إعادة الخدمة. يمكن حصر **الأعداد فقط** بالاستعلام التالي دون إخراج بيانات أشخاص:

```sql
SELECT 'Students' AS entity, COUNT(*) AS unassigned FROM Students WHERE OrganizationId IS NULL
UNION ALL SELECT 'Teachers', COUNT(*) FROM Teachers WHERE OrganizationId IS NULL
UNION ALL SELECT 'AttendanceRecords', COUNT(*) FROM AttendanceRecords WHERE OrganizationId IS NULL
UNION ALL SELECT 'BehaviorRecords', COUNT(*) FROM BehaviorRecords WHERE OrganizationId IS NULL
UNION ALL SELECT 'QuranRecords', COUNT(*) FROM QuranRecords WHERE OrganizationId IS NULL;
```

- أصبح قيد فرادة الحضور `(OrganizationId, StudentId, Date)` حتى لا يمنع سجل قديم غير موثّق كتابة سجل جديد لمدرسة مصرح بها. قد يفشل التراجع عن الترحيل إذا أصبحت هناك سجلات للطالب والتاريخ نفسيهما في نطاقات مختلفة؛ لا تتراجع دون نسخة احتياطية وخطة استعادة واختبارها.

## سياسة نقل الطالب

لا يوجد مسار نقل آلي في هذه المرحلة. لا يستطيع مدير مدرسة أو مشرف عام إعادة تسجيل طالب مملوك في مدرسة أخرى بمجرد معرفة معرّفه، ولا يُسمح بتغيير ملكية الطالب أو إعادة نسبة تاريخه ضمن هذه API.

أي نقل مستقبلي يحتاج طلبًا موثّقًا، وموافقة الجهة المخوّلة/ولي الأمر والمدرستين وفق السياسة المعتمدة، واعتماد مشرف عام، وتدقيقًا قبل التنفيذ. يجب أرشفة سجل المدرسة الأصلية ضمن ملكيتها، وإنشاء سجل مستقل للمدرسة الجديدة دون منحها سجلات المدرسة السابقة افتراضيًا، ثم اختبار الصلاحيات والروابط والخصوصية قبل الإطلاق. هذه سياسة مقترحة وليست عملية نقل منفَّذة؛ لا تغيّر `OrganizationId` مباشرة كبديل عن تصميم النقل ومراجعته.

## حدود العمل

لم تُضف عمليات تعديل أو حذف أو API نقل غير موجودة. مسائل فرادة أسماء المستخدمين والجلسات وباقي مراحل الخطة تبقى خارج المرحلة 1. نجاح اختبارات التكامل لا يغني عن تدقيق بشري، أو مراجعة تنفيذية للترحيل وخطة استعادة البيانات الفعلية.
